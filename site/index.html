      Found while building the guard: a crash the fuzzer couldn't see

      A valid packet with one non-text byte in its name (0xff, which DNS allows) passed the airlock, then crashed the whole server in the code that hands names from C++ to Rust. One 19-byte packet could take it offline. The fuzzer tested the C++ parser directly, so it never went through that code. The fix turns bad bytes into � instead of crashing, with a regression test.

      Found by trying to break it: a freeze the airlock can't stop

      Two well-formed but non-standard queries, a header with 0 questions and a reply sent as a query, passed the airlock (correctly: they're memory-safe). But 1.1.1.1 ignores them, and the first guard handled one request at a time with a 2 s wait, so each one froze it for 2 s. The fix is in the guard, not the airlock: non-standard queries now get an instant error reply, and forwarding runs on 16 worker threads, so a silent server ties up one worker instead of everything.

      Before: no reply, guard frozen 2 s eachAfter: FORMERR in under 1 ms · 5 lookups to a dead server answered together in 2.0 s

      FAQ

      Questions, answered.

      What is Basti-on?

      A Rust validator, the airlock, placed in front of a C++ DNS parser that has a deliberate out-of-bounds read in name decompression. The C++ only ever sees packets the Rust code has already proven well-formed.

      Is the C++ parser safe now?

      No. It's still memory-unsafe code, and its bug is left in on purpose. The claim is narrower: malformed input can't reach the bug, because the airlock rejects it before the C++ runs.

      Are the numbers on this page real?

      The recorded-packets results and the "Measured on this PC" figures come from the real Rust and C++ binaries, run on 10 Nov 2026. Live traffic, challenges and fuzz runs use this page's copy of validate(), which matches the Rust one on all 2,000 recorded packets.

      What does the airlock cost?

      Six benchmark runs of 1,000,000 valid packets gave −5.0% to +13.5% overhead. Background load on the test PC moved it more than the airlock did, so there's no single figure to quote yet.

      Can it be used in real code?

      Yes. examples/dns_guard.rs is a working DNS forwarder built on the library: it listens for real lookups, drops malformed ones at the airlock, lets the C++ parser read the good ones for a blocklist, and forwards them to 1.1.1.1. The DNS guard tab shows its recorded runs. Run it yourself with scripts/dns_guard_demo.sh.

      Where is the code? Can I run it myself?

      The code is public on GitHub at github.com/adisafairy/basti-on. You need Rust and a C++ compiler such as g++ (on Windows, use WSL Ubuntu). Then run cargo test for the unit tests, scripts/run_asan_demo.sh to see the crash, scripts/differential_fuzz.sh 5000 for the safety result, and cargo run --release --example bench for the overhead.

      Build story

      What I built, why it matters, what I learned

      1What I built

      • A Rust airlock (validate()) in front of a C++ DNS parser that has a deliberate out-of-bounds read, the same bug class as libtins compose_name. Every label and compression pointer is bounds-checked before the C++ runs.
      • Proof, not claims: an AddressSanitizer crash demo, a differential fuzzer, a benchmark, and check.sh, which runs them all and prints PASS or FAIL.
      • A real service on top: a DNS forwarder that answers real lookups through 1.1.1.1 with the airlock in front.
      • This page: a visual lab whose validator matches the Rust code on all 2,000 recorded packets.

      2Why it matters

      • Memory-safety bugs in parsers of untrusted input are a classic way in for attackers, and old C++ often can't simply be rewritten.
      • The airlock protects it without a rewrite: 1,471 of 5,000 fuzzed packets crashed the parser on its own, and 0 got past the airlock.
      • The danger is real: with the airlock off, one 14-byte packet made the DNS server copy 500+ bytes of its memory into the log, including pieces of other users' earlier lookups.
      • Honest limit: the C++ is still unsafe code. The claim is that malformed input can't reach the bug.

      3What I learned

      • Test the path production takes. Fuzzing the parser alone missed a crash in the Rust ↔ C++ hand-off: one valid packet with a 0xff byte aborted the whole server.
      • Memory safety isn't availability. Well-formed but odd queries froze the server for 2 s each. The fix belonged in the service (guard rules and 16 workers), not the airlock.
      • Tools have blind spots. ASan missed 20 of the over-reads in 2,000 packets because they landed in spare buffer memory.
      • Measure, don't guess. Overhead came out between −5% and +13.5% across six runs, which is too noisy to quote as one number.
